# UI Development — component style-guide pipeline

**Core idea:** a component's live source is its approved design, rendered. A
design change means changing that source; the design doc and the golden PNGs
are **generated from it**, never hand-maintained next to it. The check is the
golden diff, not the doc — a generated doc cannot be red.

**Relation to testable-apps-development (companion, read together):** that skill
owns the logic layer — pure modules, text RPC, dual-path oracles (its rules
1–6). UI components stay thin under it: markup + event forwarding, zero logic.
That split is what makes THIS pipeline cheap: a variant render plus the
shared reducer already covers a click's semantics, so component tests only
check wiring and this skill only has to organize the look. Nothing here
changes those rules; this skill covers their rule 6 "screen rendering" and
rule 7 "visual acceptance" concretely, replacing hand-made mockup acceptance.

## The two test layers

1. **Golden renders (offline, every UI task).** Two golden levels served by
   the same harness:
   - per component × variant, isolated: each interactive look of each
     presentational component has a render; the committed PNG is its contract;
   - composite screens (3–5 whole-screen states that cover the composition:
     loaded, panel open, search open, error). Isolated renders cannot see
     layout drift between components; composites can, without a window.
2. **Live whole window (milestones, not every task).** Real window + real
   data through the app's driver with numeric assertions. It covers what
   static renders physically cannot: real IPC, window lifecycle, real fonts.

## Repo lay-out

```
ui_design/
  ui_components/    ← presentational component sources; the ONLY home.
                      ui/src imports from here (no duplicate copies).
  renders/          ← committed goldens: one PNG per component × variant
    composites/     ← 3–5 whole-screen goldens
  UI_DESIGN.html    ← GENERATED by a build step from the live components.
                      Never hand-edited.
```

## Workflow for a design change (style-guide infra present)

1. **Record the decision in the spec/task, not in the doc.** The generated
   doc describes what is; future/intended design lives in spec text until
   implemented.
2. **Edit the component source** in `ui_design/ui_components/` (add a
   variant, restyle, etc.). Variants are rendered by a dev showcase
   (`?show=<name>`, `data-variant`), which is the canonical render, not a
   dev toy.
3. **Rebuild the doc + render** (`design:build` equivalent). The owner's
   approval happens here, in task review — looking at the fresh render/doc
   **before** any golden is overwritten.
4. **Run component goldens:** harness renders every variant and compares
   against `renders/`. Red = triage: intended → overwrite the affected
   renders and record before/after diff per affected render; regression →
   fix the code. A 0.000% diff where the look visibly changed means the
   changed thing is logic, not markup — go to the unit/RPC tests.
5. **Wiring check (optional, thin):** a component test asserting the
   element's event dispatches the action. Never test behavior here —
   behavior is the shared store/reducer, covered by the text-RPC skill
   layer.
6. **Milestone closes with the live check** (per the live-check rule),
   including any new named checks — accumulate, never replace.

## Infra state decides the entry point

- **Style-guide infra present** (generated doc + component-golden harness):
  the workflow above.
- **Hand-made design doc present (pre-migration):** migrate, do not
  hand-edit the mock to "match" the component — that recreates the two
  sources of truth. Migration order: (1) move presentational components
  into `ui_design/ui_components/` (single home), (2) make the doc a build
  artifact from them, (3) replace full-app golden states with component ×
  variant renders plus the composite set, (4) live checks unchanged.
- **Neither exists:** bootstrap it as part of the first UI task; do not
  accept visual changes through ad-hoc screenshots meanwhile (an OS
  screenshot is never acceptance evidence).

## Image budget

Reading images is the most context-expensive kind of reading — each image is
re-billed on every later turn of the session (documented here: 58 images,
15.5 MB read in one session; one golden read six times).

1. **One image per decision.** Each visual decision reads the image once. The
   same question is not answered by reading the same unchanged image again —
   the re-read buys nothing and pays the full context price.
2. **The outcome of a comparison lives in its numbers, not in a re-read.** The
   harness prints diff percentages per case; rereading the image to "confirm"
   what the diff already said is the process bug.
3. **Element scope over full window.** When only a part is in question, read
   the isolated variant render (the showcase's `?show=` / `data-variant`
   output), not the whole composite screen.
4. **Only visual acceptance reads images.** Every other verification is text
   and numbers: diff outputs, snapshots, evaluate results, test outcomes —
   consistent with the live-check rule and `token-economy` §2 (images: read
   only when the question is genuinely visual and no text metric answers it).

## Traps (each one has bitten a real project)

| Trap | Rule |
|---|---|
| Hand-editing the generated doc | The doc is build output; edits get wiped and mean nothing. The golden is the tripwire. |
| Approval after the golden overwrite | Once `renders/` is overwritten, "intended vs regression" is unfalsifiable. Approve on the fresh render first. |
| Rebaseline without a before/after record | Intended changes are the exception, and each one's diff is part of the task's acceptance. |
| Second home for components ("copy in the doc") | The only copy lives in `ui_design/ui_components/`; the app and the harness import it. |
| Composites skipped | Isolated renders cannot catch a panel overlapping a table; without composites, composition is only covered at milestone frequency. |
| Logic drifting into components | A component may map store state to markup and forward events. Semantics belong to pure modules (companion rules 1/6). |
| Design-oracle comparing mock vs app | If the mock is hand-made, retire it by making the doc generated (comparison becomes a tautology by construction). Do not add PAIRS-style comparison layers on top. |
| A brand-new render has no "before" | There is no diff to record for a first variant: its acceptance record is the task's recorded decision plus the fresh-render review; the committed render then becomes the contract. |
